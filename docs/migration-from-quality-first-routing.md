# Migrating from Quality-First Routing and CMR 0.5.0

The current public skill package is version 0.10.0; 0.9.0 is the preceding public package. The last public package before 0.9.0 was 0.5.0, which used CMR v1 contracts and route evidence v2. Versions 0.6.0, 0.7.0, and 0.8.0 were local profiles, not published GitHub releases. Version 0.9.0 distributed the validated 0.8.0 routing matrix and native-first correction. Version 0.10.0 preserves that matrix and transport policy while adding occurrence-bound gate evidence and current v5 dispatch contracts.

## What changes from 0.5.0

- The controller, coordinator, and semantic preflight use GPT-6.1 Sol/medium.
- Clear bounded low-risk implementation uses GPT-6 Luna/xhigh and gets independent Sol/medium task review.
- Dense approved bounded local implementation can use Luna/max under the exact implementation-phase predicates and also gets independent Sol/medium review.
- Diagnosis, audit, judgment, reconciliation, and complex local work that fails a dense predicate use Sol/medium only when the same occurrence supports no stronger gate. A supported integration/elevated-risk or hard-gate fact takes precedence in that occurrence; do not defer it to a later unit. Integration or elevated risk uses Sol/high. Hard gates, recurrence, canonical plan certification, and whole-branch final review use Sol/max.
- Controller-result-v4, preflight-result-v4, route-evidence-v5, route-decision-v4, and runtime-input-v4 remain unchanged. Current dispatch uses `cmr-dispatch-bundle-v5` and `cmr-preflight-invocation-v5`, with required `cmr-gate-evidence-v1` artifacts. New plans, ledgers, and artifacts must be created for new work.
- Every asserted hard-gate or integration/elevated-risk fact requires an occurrence-specific claim tied to the exact task brief and audited source. Each claim has a positive basis (`requested_change`, `concrete_decision`, or `critical_assurance`), a nonempty quote matching a UTF-8 brief byte slice, and a nonempty explanation. Claims cover every required gate fact exactly once in lexical order; an explicit empty sidecar is required when no gate facts are asserted.
- Bundle-v5 requires non-null `candidate_gate_evidence` on every branch. `replacement_gate_evidence` is non-null exactly for `replace`, including when its claim list is empty; `replacement_gate_confirmation` is non-null exactly for `replace` with nonempty final gate claims. All three are null/nonnull by these rules, with no implicit legacy fallback. Candidate gate evidence lives at `tasks/<task>/gate-evidence/controller.json`; replacement evidence lives at `tasks/<task>/gate-evidence/preflight.json`. The invocation-v5 binds candidate evidence; the replacement sidecar binds the exact audited preflight source. Missing, mismatched, or structurally invalid evidence blocks dispatch.
- Compile new routes with `cmr_compiler.compile_route(evidence, runtime, ontologies, *, gate_evidence=bound_gate_evidence, brief_bytes=brief_bytes)`. Both keyword arguments are required. The CLI equivalent requires both `--gate-evidence SIDECAR_PATH` and `--brief BRIEF_PATH`, for example `python -B scripts/codex_model_router.py compile INPUT [RUNTIME] --gate-evidence SIDECAR_PATH --brief BRIEF_PATH`. The CLI reads `INPUT`, optional `RUNTIME`, sidecar, and brief through frozen no-follow checks; symlinks and files with write-permission bits are rejected with one JSON error and exit 1. See the execution contract for the full binding and CLI path rules.
- The existing v4 `check-call-shape` and accounting summary cover core calls only. For complete current accounting, use `python -B scripts/codex_model_router.py check-execution-call-shape INPUT LEDGER_ROOT`; it binds confirmation attempts to replaced-preflight packets and includes each unique raw-call identity and its known usage once. Unknown usage is null and marks the report incomplete; a valid block is one confirmation call, not a retry, and extra attempts remain separate from the core retry count. Runtime/occurrence v4 records stay unchanged. See the execution contract for the required `task_preflight_evidence` mapping, Python signatures, and closed input/report schemas; accounting cannot authorize dispatch.
- A replacement with nonempty final gate claims requires one second fresh, independent Sol/medium preflight-phase adjudication before dispatch. Its closed `cmr-gate-confirmation-result-v1` contains only `schema_version` and `outcome` (`accept` or `block`); its `cmr-gate-confirmation-v1` artifact binds the exact packet and audit at `tasks/<task>/gate-confirmation/evidence.json`. A block or invalid binding ends that replacement. Replace with no final gate claims requires no confirmation, and `skip`/`accept` branches require the confirmation reference to be null. Task review and final review do not substitute for this confirmation.
- Structural checks establish byte and source binding, not natural-language truth. Preflight checks whether each quote supports the gate against the full task and phase. Context, negation, preserved constraints, filenames, test presence, and ordinary build choices alone are insufficient; do not remove facts or silently down-route.
- Native collaboration is mandatory whenever the host supports the exact occurrence. CLI is a documented, pre-disclosed, occurrence-scoped exception for a real native capability gap only.

## Preserve history

Keep sealed 0.5.0 through 0.9.0 records, packages, and commit references unchanged for historical validation. Do not rewrite old records or change their model strings. The intermediate 0.6.0-0.8.0 profiles were local, so they are not public GitHub release references. CMR evidence does not contain a package-version field that can identify its source release; do not claim that a validator rejects a record based on a nonexistent release-version field. Inspect historical CMR v4 artifacts with the retained 0.9.0 source, schemas, and package. The `qfr_legacy.py` helper is QFR-only. Current dispatch accepts only the v5 bundle and invocation; there is no implicit old-format fallback. QFR remains documentary and cannot authorize CMR dispatch.

## Safe migration sequence

1. Preserve existing QFR or 0.5.0 evidence as read-only historical input and inspect QFR with the legacy validator where applicable.
2. Reconstruct the current task brief and use exact CMR ontology IDs; omit invented route or review fields.
3. Create fresh plans, task ledgers, controller occurrences, gate-evidence sidecars, preflight evidence, safe-lane manifests, and v5 dispatch bundles under the current package. Bind each candidate sidecar to the exact controller occurrence and each replacement sidecar to its exact preflight result.
4. Run the current host dependency preflight and current CMR preflight/dispatch validation. Use the exact compiled model, effort, context, permissions, and isolation requirements. Resolve any gate-evidence rejection with fresh brief and classification while retaining the blocked history; do not start a reclassification loop.
5. For replacement results with nonempty final gate claims, obtain exactly one independent Sol/medium confirmation for the frozen packet before requesting dispatch. Then hand off through native collaboration whenever capable. A CLI exception requires the occurrence-scoped capability record and prior user notification, including expected panel-visibility loss; otherwise do not execute through CLI. Stop if no admitted transport satisfies the requirements.
6. Keep every external action blocked until its independent authorization, preview, execution, and readback are recorded.

For transport requirements, see [dependency preflight](../skills/codex-model-router/references/dependency-preflight.md) and [execution contract](../skills/codex-model-router/references/execution-contract.md).
